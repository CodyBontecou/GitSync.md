    Obsidian frontmatter syntax, in short

    Frontmatter is a block at the very top of the note: a --- line on line 1, one name: value property per line, then a closing --- line. Each property has a name, a colon and a space, then the value. Obsidian’s Properties help page lists seven types:

    TypeExampleNotes
    Texttitle: A new hopePut an internal link in quotes: link: "[[Note]]".
    List
    cast:
  - Mark Hamill
  - "[[Carrie Fisher]]"
    		One value per line, each starting with - . Quote links inside lists too.
    Numberyear: 1977
    Checkboxfavorite: trueWrite true or false.
    Datedate: 2020-08-21Format YYYY-MM-DD.
    Date & timetime: 2020-08-21T10:30:00Format YYYY-MM-DDTHH:mm:ss.
    Tags
    tags:
  - journal
  - project/alpha
    		A list, with no # and no spaces. See the Tags help page.

    Obsidian also accepts JSON frontmatter (a { … } object) and saves it as YAML. Indent with spaces: the YAML spec doesn’t allow tabs for indentation, and it says a # starts a comment, which is why - #tag in a list is read as an empty item. Nested properties (a property inside a property) are listed under Not supported in the Properties help, so Obsidian doesn’t show them in the Properties view.

    To see how a note’s Properties block looks once rendered, use the Markdown preview.

    Default and deprecated properties

    Obsidian gives three property names a special meaning: tags, aliases and cssclasses, and all three are lists. The older single-word names tag, alias and cssclass are deprecated: the Properties help page says support for them as default properties ends in Obsidian 1.9, so use tags, aliases and cssclasses.

    Obsidian Publish reserves five names: publish, permalink, description, image and cover. The checker lists them as information only. If you publish with Quartz instead, it reads draft and publish from frontmatter: see publish an Obsidian vault as a website.

    Why a property shows the wrong type

    In Obsidian, every property with the same name shares one type across the vault. If a note has a value that doesn’t fit that type, it looks wrong in the Properties view: a date written as 21/08/2020 is Text, not a Date, and True or yes may not be a checkbox. Check the shape of the value first: the checker flags the look-alikes. Then check whether another note already gave that property name a different type.

    Frontmatter and Git sync

    Properties are plain lines at the top of a .md file, so Git commits and diffs them like the rest of the note, line by line. That also means they conflict like any other line. Per the git merge documentation, a conflict happens when both sides change the same lines. If two devices change the same property line, for example when a plugin rewrites a modified-date property on every edit, you get a merge conflict on that line.

    To see exactly which property lines changed between two versions, paste both into the Markdown diff. To resolve a conflict that has already happened, follow resolve Obsidian Git merge conflicts on iPhone. If you want device-specific files out of the repository, the Obsidian .gitignore generator writes the rules.

    Frequently asked questions

    Does this upload my note?

    No. The page has no external scripts and makes no network requests while you use it. Pasted text is read in your browser and is not saved.

    Can I use JSON frontmatter in Obsidian?

    Yes. Obsidian Help says JSON frontmatter is valid: Obsidian reads it and saves it as YAML. Paste it here to see the YAML equivalent.

    Why is my tag invalid?

    Obsidian Help says a tag can’t contain spaces, needs at least one non-numeric character (1984 is invalid, y1984 is valid), and can use letters, numbers, underscores, hyphens and forward slashes for nesting.

    Does Obsidian support nested properties?

    Obsidian Help lists nested properties under Not supported: they aren’t shown in the Properties view. The checker flags them as a warning, not an error.
