Share an Obsidian vault with others using GitHub.

Put the vault in a private GitHub repository, invite your partner, group or team, and have each person clone it on desktop, iPhone, iPad or Android. It is shared history, not live co-editing, so this guide also covers the token trap and the habits that prevent most conflicts.

Quick answer
  1. Put the vault in a private GitHub repository and add each person under Settings → Collaborators → Add people. They accept the invitation.
  2. Each person clones the repo: the Obsidian Git plugin on desktop, GitSync.md on iPhone and iPad, GitSync.md on Android.
  3. Collaborators should not use a fine-grained token on someone else’s personal repo. Sign in with GitHub, use a classic token, or move the repo into an organization.
  4. Git is not live co-editing. Two people can work in the same vault, but not type in the same note at the same moment. Pull before you edit, commit small and often.

What you need

  • A GitHub account for each person.
  • One private repository that holds the vault.
  • Obsidian on each device, plus a way to run Git on it (see step 3).

Step 1 (owner): put the vault in a private repo

Create a private repository and push the vault to it. The full walkthrough, including the Obsidian Git plugin settings and adding a phone, is in Sync Obsidian with GitHub, so it isn’t repeated here. Before the first push, set up the ignore rules in the section below so personal workspace files don’t land in the shared history.

Step 2 (owner): add collaborators

  1. Open the repository on GitHub and go to Settings → Collaborators → Add people.
  2. Enter each person’s GitHub username or email and send the invitation.
  3. Each person accepts the invitation from the email or from GitHub’s notifications.

GitHub documents the steps in Inviting collaborators to a personal repository. Collaborators on a personal repository get read and write access; see Permission levels for a personal account repository. Finer roles, such as read-only, need the repository to live in a GitHub organization.

Step 3 (each collaborator): clone the vault

Desktop

Clone the repository into a folder, open that folder as a vault in Obsidian, and install the Obsidian Git plugin. The plugin guide covers the settings.

iPhone and iPad

In GitSync.md, clone the repository into a folder that Obsidian can open. Clone a GitHub repository on iPhone shows the steps, and Obsidian Git on iPhone and iPad explains how to open the folder as a vault.

Android

Follow Sync an Obsidian vault with Git on Android. GitSync.md is on Google Play.

Teams on GitLab can do the same with Obsidian and GitLab. GitSync.md also supports Bitbucket, Gitea and Forgejo remotes.

The token trap for collaborators

The owner’s setup usually works with a fine-grained token scoped to their own repository. A collaborator who copies that approach hits a wall. GitHub’s documentation on personal access tokens lists this among the limitations of fine-grained tokens:

“Using fine-grained personal access token to contribute to repositories where the user is an outside or repository collaborator.”

In other words, on someone else’s personal repository, a fine-grained token isn’t the right tool. Pick one of these:

  • Sign in with GitHub in GitSync.md instead of pasting a token.
  • Use a classic personal access token with repository access.
  • Move the repo into a GitHub organization (the owner’s call), which also gives you finer roles.

The token link generator builds a fine-grained link for repositories you own; don’t use it for a repo someone else owns.

What to commit and ignore in a shared vault

Obsidian writes window layout to .obsidian/workspace.json and .obsidian/workspace-mobile.json. Every person’s copy differs, so committing them makes noise and conflicts. Add .obsidian/workspace*.json to .gitignore. Plugin settings that differ per person can be ignored too, while settings you want everyone to share can stay. Use the .gitignore generator and read the Obsidian .gitignore guide. If a workspace file is already tracked, ignoring it doesn’t remove it; the guide covers that.

House rules that prevent conflicts

Git can merge edits to different parts of a note. Per the git-merge documentation, when two sides change the same lines, Git stops and leaves a conflict for a person to resolve. These habits keep that rare:

  • Pull before you edit, every time you open the vault.
  • Commit and push small and often, so the window for overlap stays short.
  • One folder per person for drafts. Move finished notes into the shared area.
  • Keep .obsidian/workspace*.json out of the repo.
  • Don’t edit the same note at the same time. Say so in chat when you take a note.
  • Resolve conflicts; don’t force-push over a teammate’s work.

When a conflict happens

Pull, find the files Git marks, and keep one version or combine both by hand. On iPhone and iPad, GitSync.md’s Conflict Center lets you choose ours, theirs or an edited result; the conflict guide walks through it. To compare two versions of a note, paste them into the Markdown diff tool.

Read-only sharing

If others only need to read the notes, you don’t need collaborators. Publish the vault as a website instead.

FAQ

Can two people edit the same note at the same time?

Not live. Git has no co-editing or presence. Each person edits a local copy and syncs through commits. Edits to different parts of a note usually merge; edits to the same lines need a manual resolution.

Does everyone need Obsidian Sync?

For Obsidian’s shared vaults, yes: Obsidian’s help says all collaborators must have an active Sync subscription. With a GitHub repository, they don’t; each person needs a GitHub account and a Git client.

Can I share only one folder?

Not with one repo. Git shares the whole repository, and collaborators on a personal repo can read and write all of it. Keep the shared part in a separate vault or repo.

Is the repo private?

Only if you make it so. Choose Private when creating it, and only invited people can see it.

What if a collaborator can’t push?

Check that they accepted the invitation and aren’t using a fine-grained token; see the token trap.
