# Initializing an iPhone folder and publishing it to GitHub

Exploration and follow-up review against repository commit `6698950`, Apple's directory-access documentation, GitHub's REST documentation, and the bundled libgit2 headers/binary. Reviewed on October 7, 2026. The original assessment is preserved below; the implementation follow-up records what has since been built. Physical-device and live GitHub qualification remain outstanding.

## Implementation follow-up

The first publication flow is implemented under **Add Repository → Publish a Folder**. It inspects a selected local folder without changing it, reviews individual files and author identity, prepares one initial `main` commit, then requires a separate action to create a private personal GitHub repository and publish that saved commit. Existing working files and ignore/attribute files are preserved, along with the reviewed executable mode. Unselected existing paths receive literal local rules in `.git/info/exclude`; these rules persist for later staging, but do not cover newly created paths automatically. New repositories start excluded from Background Sync.

The supported storage allowlist is an actual local application `Documents` directory selected through Files, including GitSync.md's own location. Merely matching a container-like directory name is insufficient. Cloud/file-provider locations, symlinks, packages, existing/enclosing/nested Git metadata, Git LFS, and attributes that transform selected file contents are gated. Limits are 10 MiB per selected file, 10,000 selected files, 256 MiB selected contents, and 50,000 inspected regular files. A conservative storage estimate is checked before `.git` is reserved; available capacity can change afterward, so it cannot guarantee completion.

[`FolderGitService`](../Sync.md/Services/FolderGitService.swift) owns inspection, metadata ownership, immutable-tree preparation, transport checks, and upstream setup. [`FolderPublicationCoordinator`](../Sync.md/Services/FolderPublicationCoordinator.swift) owns the durable phases and guarded recovery. Its [`journal`](../Sync.md/Services/FolderPublicationStore.swift) lives outside the working folder and contains bookmarks and identity, with credentials kept in the existing credential store. It pins both the GitHub numeric account ID and returned repository ID, persists intent before creation/push, and reconciles lost responses against actual references. Ambiguous creation requires explicit adoption; missing `main` alone never permits publication to an otherwise nonempty repository.

[`AppState`](../Sync.md/Models/AppState.swift) registers confirmed publication idempotently, preserves user-owned-folder deletion protection, and holds the publication guard across registration. Other import/discovery and clone paths cannot register or replace a folder with unfinished publication progress. Revoked bookmark access preserves saved Git state and offers reconnection. An unavailable grant cannot select a writable fallback folder or delete previous files while adopting a clone location. The ordinary LFS staging pass now receives ignore-aware index candidates, closing the ignored-file staging hole identified in the original assessment.

Automated verification passed **71 distinct targeted tests** on the iOS 26.5 simulator: 20 native folder tests, 18 workflow/recovery tests, 16 mocked REST tests, 15 existing staging/push/clone/relink regressions, and two UI flows. Native fixtures verify exact published bytes against local bare remotes, upstream tracking, Unicode names, executable mode, insufficient storage, and isolation from unreviewed LFS pointers in the staging index. UI flows cover the publication entry and an existing local-remote clone. These are focused checks, not a claim that the complete repository test suite ran; no live GitHub repository is created by them.

Remaining qualification includes a physical iPhone picker/bookmark/relaunch test, live private-repository creation and push with the supported OAuth permissions, server push-protection failures, and interruption at each durable phase. Correction of rejected unpublished commit contents, standalone local-only initialization, organizations, LFS publication, and provider support are follow-up scope.

## Conclusion

Yes, at the platform/library level. GitSync.md has the pieces to create a new local Git repository or convert an existing, writable, user-selected Files directory into a repository **in place**, then publish it to GitHub. Initialization can happen offline when the required files are locally available; remote creation and pushing need network access. No shell-based Git process is necessary. [Apple directory access][apple-folders], [bundled package](../Packages/Clibgit2/Package.swift), [libgit2 initialization API](../libgit2.xcframework/ios-arm64/Headers/git2/repository.h), [GitHub repository creation][github-create].

The main unresolved feasibility question is reliable **in-place Git storage on external providers**, not whether `git init` exists. The current publication operations also need changes before they can safely bootstrap and retry a new repository, especially with Git LFS. Treat support for a tested local location as the first milestone, and cloud-provider support as a separate qualification gate.

This does not mean the app can browse every directory on the phone, or that every cloud file provider is suitable for an in-place Git working copy. The boundary is a directory the user can select and the app can actually read/write. Apple documents security-scoped access outside the app's own container, including providers, and explicitly requires handling access failures. [Apple directory access][apple-folders].

## Why iOS permits it

Apple's “Providing access to directories” documentation states that, since iOS 13, the document picker can return a security-scoped URL granting recursive access to a selected directory. The grant includes **new items subsequently added** to that directory. The app may enumerate, add, remove, or modify files and save a bookmark for future launches. Creating `<selected-folder>/.git/` fits that mechanism. The project targets iOS 17. [Apple directory access][apple-folders], [`project.pbxproj`](../Sync.md.xcodeproj/project.pbxproj).

The app already enables `UIFileSharingEnabled` and `LSSupportsOpeningDocumentsInPlace`. Its existing bookmark flow is reusable. Apple requires security-scoped access to remain active during operations and file coordination for reading/writing external directory contents. An implementation must account for libgit2's direct filesystem operations as well as Foundation calls. [`Info.plist`](../Sync.md/Info.plist), [`AppState`](../Sync.md/Models/AppState.swift), [Apple directory access][apple-folders].

A folder privately stored by another app cannot simply be addressed by an arbitrary path; it must be available through the supported picker/access mechanism. Files-visible, writable folders are candidates; read-only or inaccessible locations must fail without changing their contents. This is the same sandbox boundary already documented by [`GitRepoScanner`](../Sync.md/Services/GitRepoScanner.swift).

## Suggested implementation flow

The following was the proposed flow at the assessment commit. The implementation follow-up above identifies the delivered first scope:

1. **Choose a folder**, or create a new folder in GitSync.md storage or a user-granted parent. Keep the grant active and persist its bookmark and storage ownership. Resolve the bookmark before every resumed workflow; failed resolution/access must lead to reconnecting the folder, not a substitute path.
2. **Inspect before mutation**: confirm access, enumerate all intended content with errors surfaced, and detect Git metadata at the selected root, accessible ancestors, and descendants. A `.git` file also counts; reject unsupported worktrees, bare repositories, and embedded repositories rather than flattening them accidentally. Ancestors outside the grant may be inaccessible: do not present a partial check as proof that no enclosing repository exists. Review paths, sizes, exclusions, and any proposed `.gitignore`/`.gitattributes` edits. Preserve existing rules.
3. **Initialize locally** using `git_repository_init_ext`, non-bare, with `initial_head = "main"` and `GIT_REPOSITORY_INIT_NO_REINIT`. These controls are available in the [bundled header](../libgit2.xcframework/ios-arm64/Headers/git2/repository.h). Initialization adds Git metadata rather than replacing the selected working files.
4. **Prepare and review the local commit before creating a remote**. Choose author identity (including a privacy-preserving email choice) and commit message before committing. Stage only approved paths, validate the resulting index/tree and size/LFS requirements, and save the initial commit. If files change between review and staging, require a fresh review of affected content. Do not implement selection with unrestricted `stageAll`. Persist the approved tree/commit OID so publication and retries send the same content. Empty or entirely ignored folders must reach an explicit choice before any remote is created; Git does not preserve empty directories.
5. **Review publication settings**: GitHub account, repository name, private visibility by default, and the saved commit/author metadata to upload. Changing committed content or identity requires a new reviewed commit OID. Local initialization and uploading should have separate consent. Freeze the chosen account/destination for this attempt; switching the active account must not silently retarget it.
6. **Create an empty remote** with `POST /user/repos`, e.g. `{"name":"my-notes","private":true,"auto_init":false}`. Do not request remote README, license, or ignore-file initialization: the local initial commit should establish the history. Save the returned repository ID, owner, visibility, and canonical clone URL. An organization destination uses `POST /orgs/{org}/repos` and must satisfy organization permissions/policy. [GitHub repository creation][github-create], [organization creation][github-org-create].
7. **Configure `origin` and publish the saved commit through an explicit first-publication path**. Reuse native primitives after addressing the missing-branch and LFS gaps below. Check the actual remote references; a missing `main` alone does not prove the remote is empty. Require the destination branch to remain absent during transport negotiation, stop if it appears unexpectedly, and never force-push. This guards the destination ref; repository-wide emptiness is a preflight check, not an atomic guarantee across every branch/tag. Establish fetch configuration, upstream tracking, and Unicode configuration explicitly, then verify the remote branch points to the saved OID and refresh persisted status. Enable ordinary sync only after this completes. [`LocalGitService`](../Sync.md/Services/LocalGitService.swift).
8. **Retain progress on failure**. A created remote or saved local commit should remain available for retry; failure must not delete the original folder or create another remote blindly. `LocalCommitSavedNotPushedError` is useful feedback, but a timeout/cancellation may leave the remote outcome unknown. Reconcile actual local/remote state before retrying.

Creating a remote is optional: the same local workflow could publish to an already-created **empty** GitHub repository. An existing remote with commits is a different history-reconciliation case and should not be overwritten implicitly.

## Publication invariants and recovery

Use a durable publication record separate from ordinary sync status. It should hold a workflow ID, folder bookmark/canonical identity, user-owned versus app-managed storage, selected GitHub account, requested owner/name/visibility, approved commit OID, returned remote identity, and last confirmed phase. Store credentials in the existing credential store, not in this record. Persist intent before external mutation, then persist confirmed outcomes; filesystem and GitHub writes cannot form one atomic transaction.

| Interrupted phase | Required recovery behavior |
| --- | --- |
| Initialization or staging | Reopen and validate metadata/index; distinguish partial initialization from a usable unborn repository. Preserve user files and existing Git metadata. Never delete an ambiguous `.git` directory as automatic cleanup. |
| Local commit saved | Reuse the saved OID. If HEAD moved or the intended tree changed, stop for a new review rather than committing whatever is now present. |
| Repository creation response lost | Mark creation outcome unknown. Reconcile the requested owner/name with GitHub before another POST. A same-name repository, even an empty one, is not proof it belongs to this attempt; confirm identity/visibility and require explicit adoption if provenance remains ambiguous. A REST `404` can also mean missing permission to a private repo; it does not prove creation failed. [GitHub troubleshooting][github-troubleshooting]. |
| Remote created, push pending | Resume against the saved repository identity and URL; expose its link. Cancellation leaves the remote and local commit intact. Remote deletion is a separate explicit action. |
| Push response lost | Read the destination branch: the saved OID means success; absent branch permits a guarded retry; unexpected history requires attention. Do not create another initial commit. |
| Push confirmed, registration/tracking incomplete | Finish local configuration and registration idempotently. Do not repeat repository creation or publication. |
| Bookmark revoked, folder moved, or provider unavailable | Block operations and offer reconnection. Do not interpret inaccessible metadata as a deleted repo or fall back to app storage with the same folder name. |

Put this workflow behind one publication module whose interface exposes inspection, preparation, publication, and resumption results. The UI should not independently orchestrate initialization, staging, remote creation, and retries. Keep provider coordination and Git transport details inside the implementation, using the existing repository lease for composite local operations. Release provider coordination before long network waits; the lease and security scope have different lifetimes. This keeps the state and failure handling in one place without inventing a general abstraction for every possible hosting provider.

## Engineering issues beyond adding a button

- **Unborn/empty repository state:** `repoInfo()` currently requires `git_repository_head` to succeed; `RepoConfig.isCloned` means “has a nonempty commit SHA”; `VaultView` and many AppState operations use that flag. An initialized repository with no commits would fail registration or appear to need cloning. Support local-ready/no-commit and local-only/no-remote states explicitly for an init-only feature. A publish-only flow could register after creating the initial commit, but would still need recoverable intermediate state. [`LocalGitService.repoInfo`](../Sync.md/Services/LocalGitService.swift), [`RepoConfig.isCloned`](../Sync.md/Models/RepoConfig.swift), [`VaultView`](../Sync.md/Views/VaultView.swift), [`AppState`](../Sync.md/Models/AppState.swift).
- **First push is not ordinary sync:** `RepositoryPushRunner` reads `repoInfo` before staging, while reconciliation rejects `.remoteBranchMissing`. Its saved-commit retry depends on `aheadBy > 0`, but `pullPlan` reports zero ahead/behind when the remote branch is absent. These paths cannot simply be reused to bootstrap an unborn repo or retry the first commit against an empty remote. Add an explicit publication path with saved-OID and remote-absence expectations. Upstream setup is also new work: `setRemoteURL` does not establish branch tracking, and current sync status is `.unknown` without an upstream. Keep initial publication on native Git transport; GitHub's REST “Create a reference” endpoint cannot create refs in an empty repository, so existing blob/tree/commit helpers are not a drop-in bootstrap alternative. [`RepositoryPushRunner`](../Sync.md/Services/RepositoryPushRunner.swift), [`LocalGitService.pullPlan` / `setRemoteURL` / `syncState`](../Sync.md/Services/LocalGitService.swift), [GitHub reference creation][github-refs].
- **Never reuse clone as import:** `AppState.clone` removes an existing destination directory before cloning. It is not a safe way to convert a populated user-selected folder. Keep initialization separate and preserve the existing user-owned-folder deletion protections. [`AppState.clone` / `removeRepo`](../Sync.md/Models/AppState.swift), [`RepoConfig.isExternalLocalRepository`](../Sync.md/Models/RepoConfig.swift).
- **Exclusions currently have an LFS hole:** `stageAll` first uses ignore-aware `git_index_add_all`, then calls `cleanAndStageLFSFiles` without a candidate path list. That pass enumerates regular worktree files without checking Git ignore rules and inserts matching LFS pointers directly into the index. An ignored file matched by existing LFS attributes, or by enabled auto-tracking, can therefore become staged. This is a source-inspected risk, not a reproduced device result. Require ignore-aware LFS staging restricted to approved paths, then verify the final tree contains no unapproved paths. Decide whether exclusions persist via `.gitignore` or local `.git/info/exclude`; a one-time unchecked box must not be presented as protection from later sync. [`LocalGitService.stageAll`](../Sync.md/Services/LocalGitService.swift), [`GitLFSService.cleanAndStageLFSFiles` / `enumerateWorktreeFiles` / `addPointer`](../Sync.md/Services/GitLFSService.swift).
- **LFS first-publication retry is incomplete:** `pushedChangePaths` returns an empty list when no upstream exists; `pushCurrentBranch` interprets that as no LFS objects to upload. Consequently, `commitLocal` followed by `pushCurrentBranch`, or a retry after failed initial publication, can omit required LFS uploads. Current pointer lookup also reads the mutable index rather than the saved commit tree. Resolve size checks and LFS objects from the history being published, with explicit no-upstream handling, and upload those objects before updating Git refs. Gate LFS support until this works; uploading Git refs alone is not successful publication of LFS content. [`LocalGitService.pushCurrentBranch` / `pushedChangePaths`](../Sync.md/Services/LocalGitService.swift).
- **Cloud-provider validation:** permission to add files establishes feasibility, not reliable Git transactions for every provider. Test `.git` contents, exclusive lock creation, atomic renames, downloaded/evicted files, interruptions, and concurrent changes on actual providers. Provider replication of individual metadata files across devices must not be assumed to be an atomic Git transaction. Existing coordination covers selected file replacements, not all libgit2 reads/writes. Define and prove how those operations stay inside coordinated access without nested-coordination deadlocks. A copy into app-managed storage is a possible fallback, but is not in-place synchronization of the original folder. [Apple directory access][apple-folders], [file coordinator behavior][apple-coordination], [`RepositoryOperationCoordinator`](../Sync.md/Services/RepositoryOperationCoordinator.swift).
- **Bookmark failures need a distinct state:** `resolveVaultBookmark` can return without resolving a URL; `vaultURL` then falls back to app storage. `validateClonedRepos` interprets a missing `.git` as no longer cloned. A resumed publication must distinguish unavailable access from missing local data, and must never initialize/clone a fallback directory when the user's selected folder is unavailable. [`AppState.resolveVaultBookmark` / `vaultURL` / `validateClonedRepos`](../Sync.md/Models/AppState.swift).
- **Automation must skip unfinished publication:** `RepoAssistSettings.disabled` defaults to `excludedFromAutomaticSync = false`; `PremiumRuntime` can automatically enroll a repository once `isCloned` becomes true. Merely registering a local commit with `assist = .disabled` is insufficient. Persist a publication-in-progress state that enrollment skips, or an explicit exclusion, through preparation and recovery. Require a deliberate transition to ongoing sync after successful publication; its all-changes staging must continue respecting persistent exclusions. [`RepoAssistSettings`](../Sync.md/Models/PremiumModels.swift), [`PremiumRuntime.reconcileAutomaticRepository`](../Sync.md/Services/PremiumRuntime.swift), [`RepositoryPushRunner.stageAllLocalChanges`](../Sync.md/Services/RepositoryPushRunner.swift).
- **Authentication:** the current OAuth login requests `repo user:email`; granted `repo` scope supports creating public/private repositories. Do not assume every pasted token has equivalent permissions or covers a newly created repository. Creation permission and permission to push contents are separate checks; fine-grained tokens must cover the chosen owner, applicable creation permissions, and the resulting repository's contents. Importing `.github/workflows` can additionally require OAuth `workflow` scope, which this login does not request. Validate behavior using the REST version pinned by this app (`2022-11-28`), rather than inferring every accepted permission combination from the latest documentation. Preserve actionable validation, authorization, and rate-limit errors instead of treating every failure as a name collision or expired login. [`oauth-server/api/auth/login.ts`](../oauth-server/api/auth/login.ts), [`GitHubService.request`](../Sync.md/Services/GitHubService.swift), [GitHub creation scopes][github-create], [OAuth scopes][github-scopes], [fine-grained permissions][github-pat].
- **Server rejection can require a new approved commit:** GitHub can reject a push for secrets, private author-email exposure, or repository policy. Preserve the reason and the user's files. If a secret is in an unpublished initial commit, a later deletion commit still carries it in history: offer correction of the unpublished history with renewed review and a new saved OID. Do not automatically bypass push protection or rewrite published history. [GitHub push protection][github-push-protection], [author-email blocking][github-email-blocking].
- **Initial contents and resource limits:** review sensitive files (`.env`, credentials, private notes), hidden files, symlinks, packages, and embedded repositories explicitly. Do not follow symlinks outside the grant or claim a partial/failed enumeration is complete. Git submodules represent another repository by a commit reference, not a recursive copy of its files. Current commit methods require staged changes. GitHub blocks regular Git files larger than 100 MiB, but this app's push validator currently rejects non-LFS blobs over **10 MiB**, including text files; default auto-tracking recognizes known binary extensions or large binary files, so it does not solve every rejected file. Preflight file count, available storage, and total bytes as well: staging adds Git objects, LFS caches can add copies, and pack creation needs working space. Keep the first upload in the foreground with resumable cancellation; do not promise completion after iOS suspends the app. [`GitLFSService.validateNoLargeNonLFSBlobs` / `GitLFSAutoTrackingPolicy`](../Sync.md/Services/GitLFSService.swift), [GitHub size limits][github-large-files], [Git submodules][git-submodules], [file coordinator lifecycle][apple-coordination].

## Recommended first scope and proof

Start with an existing, locally available, writable folder in a tested Files location → new private repository in the signed-in user's personal GitHub account. Scope the first release to ordinary files within the app's size policy unless the LFS prerequisites above are fixed and verified. Keep automation disabled throughout preparation/recovery. Add standalone initialization and organization/cloud-provider breadth deliberately rather than claiming universal filesystem support.

Run the storage proof first: initialize, stage, commit, reopen, and verify a small fixture on a physical iPhone in the target location, with coordinated access, an external editor, and relaunch. If safe metadata operations cannot be demonstrated, narrow supported locations or offer an explicit copy workflow before building the broader publication UI.

Before shipping, validate on a physical iPhone:

- Original files remain byte-identical after initialization; existing metadata, accessible enclosing repositories, `.git` files, and embedded repositories are handled without accidental reinitialization or nesting.
- Reviewed files become the initial `main` commit and are visible on GitHub; excluded secrets remain local. Check an ignored LFS-matched binary and an ignored auto-tracking candidate in the final index/tree, not just the preview. New or modified files after review cannot enter publication silently.
- After relaunch, bookmark access still works and subsequent edits can be committed/pushed.
- Kill the app after each durable phase, lose the create/push response after server success, and resume: no duplicate repositories/commits, no automatic adoption of a same-name repo, and local registration completes once.
- Missing/revoked/stale bookmarks preserve the original folder and block fallback initialization. Changing the active GitHub account cannot retarget a pending operation.
- A destination branch created/advanced between inspection and push causes attention without overwriting history. Preflight detects existing branches/tags; a missing `main` in a nonempty remote is not treated as an empty repo.
- Registering a saved local commit cannot trigger automatic enrollment or upload before publication completes and ongoing sync is enabled. A blocked secret/email push offers correction without uploading the rejected original history on retry.
- Empty/all-ignored folders, Unicode and case-sensitive names, symlinks, packages, insufficient storage, and files over the app's 10 MiB policy behave intentionally.
- If LFS is supported, retry after local commit or LFS upload without an upstream; verify required objects can be downloaded from GitHub even when the local index/worktree changed after the saved commit.
- Test iCloud Drive and each third-party provider separately before advertising support.

The original assessment did not change application code, create a GitHub repository, or run simulator/physical-device tests. Subsequent implementation and verification are recorded in the follow-up above.
