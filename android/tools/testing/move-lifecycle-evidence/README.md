# Move review screen and request ownership

Move preparation previously used a volatile owner check followed by a separate StateFlow write, and the screen cleared review state on entry only. A late producer could race a clear or publish after its screen closed. `MoveReviewState` now serializes screen ownership, request invalidation/publication, exact-review claims and completion cleanup under one lock. `MoveRepositoryScreen` opens an owner in DisposableEffect, closes only that owner on disposal and passes the owner to preparation, clearing and confirmation. Disposal from an older screen cannot clear a newer screen's review.

Closing or replacing a screen invalidates pending requests. Accepted filesystem work keeps its reviewed authority until completion, even when its screen closes; a new screen cannot cancel that accepted move or start another one. Its automatic completion callback runs only while its original screen owner is current. Review cleanup runs in the ViewModel mutation's outer finally, including initial-load cancellation or catalog-read failure before the action begins. Initial-load waiting is now inside that try/finally. Existing checkout/catalog/credential checks and durable move behavior remain connected.

Ten new app JVM tests exercise the production review state, with generated Git repositories and actual preparation/move leases where relevant: leaving during blocked preparation, superseding a folder request, late old-screen disposal, departed-screen requests/confirmation, accepted moves after closure/reopening, failed filesystem validation, folder-clear revocation, claim release and repeated stale cleanup. Successful moves preserve exact checkout bytes; rejected late preparation publishes no review, and changed-checkout failures preserve work and create no journal. The two cleanup tests manually invoke the production state's finish operation; they do not trigger an Android catalog-read error or execute the ViewModel mutation wrapper. The prior seven move-consent regressions also pass.
