# Managed deletion request qualification

The production Settings deletion path now uses `withRepositoryDeletionReview` to acquire the reviewed checkout lease and then recheck the exact active review, current saved catalog record, app-managed storage ownership and canonical catalog/plan path pairing before invoking deletion and history completion. Default keep-files removal remains separate. The catalog lookup now happens inside the lease. The path-pairing guard also rejects an accidentally mismatched catalog/plan request. This is request-authority hardening and coverage; no pre-fix runtime reproduction is claimed in this phase.

Eight new real-Git JVM cases pass: queued cancellation, same-folder rereview, another-folder review, catalog removal, changed alias, changed managed-storage flag, mismatched plan/catalog path and successful deletion of exactly the reviewed checkout. Rejections enter no destructive action and preserve both generated repositories byte for byte. The successful case uses the actual core deletion service and preserves the other checkout. These tests execute the production request gate; they do not execute Android preferences/history persistence, screen-owner lifecycle or UI navigation. The existing core limits still apply: deletion covers current whole-folder contents, does not pin every worktree byte, and is not an OS transaction against uncoordinated filesystem writers.
