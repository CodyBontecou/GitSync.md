# Persisted sign-out session reconciliation

Preparing a Settings sign-out review now rereads and normalizes encrypted session state under the auth-manager lock. A stale displayed revision returns before that read. If the persisted state differs, the manager publishes the refreshed accounts/token/profile and a new revision, then returns no review. A subsequent click on the refreshed account is required. A mismatch found inside confirmation's store callback also triggers reconciliation without disconnecting the newly observed account. Missing records publish signed-out state. Read failures retain the prior published session, expose the existing storage error and permit retry.

Reconciliation invalidates plaintext profile/repository caches even when the token is unchanged. The ViewModel refreshes its profile from current cached session fields on a same-token revision, so an old user object cannot override the refreshed Settings label while networking waits. Current search/repository ownership rules are retained. Requests for an old token are cancelled and the new account's profile load starts. Confirmation still checks the exact review and freshly read persisted state before publication; reconciliation never automatically confirms a replacement account.

Seven new cases extend the sign-out suite to 21 cases. They cover preparation after an external switch, externally deleted state, changed profile with the same token, read failure/retry, an actual second auth-manager switch using the synthetic store, confirmation rejection followed by fresh consent, and stale entry that must not read or reconcile away a newer dialog. The same-token case seeds a token-owned stale plaintext profile/repository cache and verifies its removal plus fresh auth-cache and ViewModel login/name publication. The earlier changed-store case now verifies cancellation of the old token's load and dispatch of the refreshed token's load. Actual auth-manager/ViewModel/session-lock code executes with a mocked encrypted store and memory-backed preference boundary. The API fixture makes no network requests.
